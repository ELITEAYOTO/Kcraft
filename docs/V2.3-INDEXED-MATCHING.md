# KCraft V2.3 — Indexed Matching

## Hot path avant

```text
findMatchingRecipe
  -> toutes les recipes
  -> filtre table
  -> CraftMatrixTransaction.matches
  -> consumeOnce
  -> clone de matrice
```

Même un simple preview payait donc le coût d'une transaction de consommation.

## Hot path V2.3

```text
ItemStack[] matrix
      |
      v
MatrixSnapshot             1 fois
      |
      v
MatrixFingerprint          O(slots)
      |
      v
RecipeIndex                O(1)
      |
      v
petit bucket candidats
      |
      v
RecipeMatcher exact        0 clone
```

`CraftMatrixTransaction.consumeOnce()` reste utilisé uniquement au moment où
une vraie transaction doit consommer les items.

## Fingerprint

Le fingerprint primaire contient uniquement des données qui ne peuvent pas
produire de faux négatif :

- table ;
- nombre de slots occupés ;
- multiset des Material présents.

Exemple :

```text
tier1|3|DIAMONDx1,STICKx2
```

La geometrie, la data, le nom, le lore et le NBT sont vérifiés ensuite par le
matcher exact.

## ItemSnapshot

Material / data / amount / meta sont capturés une seule fois.

NBT est lazy :

```text
recipe sans NBT
-> 0 NBTItem

plusieurs candidats NBT sur le même slot
-> 1 seul NBTItem pour ce slot
-> valeurs NBT mises en cache par clé
```

Cela élimine une grande partie des créations répétées de `NBTItem` observées
dans le moteur historique.

## SHAPED

Le matcher :

- teste les offsets autorisés ;
- teste le miroir uniquement si activé ;
- compare uniquement les cellules occupées ;
- ne clone aucun ItemStack.

Comme `occupiedCount == shapedCells.size()`, une fois toutes les cellules du
pattern validées, aucun item supplémentaire ne peut exister hors pattern.

## SHAPELESS

Les ingrédients sont déjà triés par spécificité depuis V2.2.

V2.3 utilise un backtracking exact avec un bitmask `int`.

Tables max = 5x5 = 25 slots, donc aucun `boolean[]`/`int[]` n'est nécessaire
par candidat.

## Scope

Le custom GUI profite maintenant du nouveau moteur via
`IndexedCraftManager.findMatchingRecipe()`.

Les chemins vanilla/KHope qui utilisent encore directement
`VanillaRecipeResolver` / `CraftMatrixTransaction` seront refondus avec la
future couche plateforme/fork.

## API dynamique

Les recettes ajoutées dynamiquement après compilation gardent temporairement
le fallback historique jusqu'à V2.6.

C'est acceptable pendant la refonte et évite de complexifier V2.3.
