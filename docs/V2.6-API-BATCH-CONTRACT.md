# KCraft V2.6 — API V2 + Batch Contract

## Pourquoi les events legacy ne sont pas supprimés immédiatement

Kjobs actuel écoute `KcraftPostCraftEvent`.

Pour Artisan, il donne l'XP une fois par event.
Pour certaines quêtes/Pilleur, il utilise la quantité du résultat.

Passer directement de 64 events à 1 event sans modifier Kjobs changerait donc
le gameplay.

V2.6 introduit une migration en deux contrats.

## Contrat legacy enrichi

`KcraftPostCraftEvent` garde son ancien constructeur.

Nouveaux getters :

```java
event.getExecutionSource();
event.getTransactionId();
event.getBatchIndex();
event.getPlannedBatchSize();
event.isLegacyBatchElement();
```

Pendant un shift-craft :

```text
64 legacy events
source = SHIFT_BATCH
transactionId = même UUID
batchIndex = 0..63
```

Kjobs actuel continue donc de fonctionner exactement comme avant.

## Nouvel event agrégé

À la fin du batch :

```java
KcraftBatchCraftEvent
```

avec :

```text
transactionId
plannedCrafts
attemptedCrafts
successfulCrafts
failedCrafts
totalResultItems
cancelled
results[]
```

Chaque `CraftBatchResult` contient :

```text
sample ItemStack
craftOccurrences
itemCount
```

Exemple : 64 crafts de 4 flèches :

```text
craftOccurrences = 64
itemCount = 256
```

## Migration future Kjobs

Kjobs V2-aware pourra :

1. ignorer `KcraftPostCraftEvent` si `isLegacyBatchElement() == true`;
2. écouter `KcraftBatchCraftEvent`;
3. Artisan XP : utiliser `craftOccurrences`;
4. quêtes item : utiliser `itemCount`;
5. Pilleur/CIT : matcher `CraftBatchResult.getSample()` puis multiplier.

Résultat :

```text
avant 64 crafts
-> 64 callbacks Kjobs

après migration
-> 1 callback batch
```

Sans nouvelle modification Kcraft.

## CraftExecutionContext

Le CraftManager historique n'a pas besoin d'être réécrit juste pour transporter
source/transaction.

Le listener ouvre :

```java
try (CraftExecutionContext.Scope ignored =
        CraftExecutionContext.enter(...)) {
    craftManager.executeCraft(...);
}
```

L'ancien constructeur `KcraftPostCraftEvent(...)` récupère automatiquement le
contexte ThreadLocal.

Aucune référence Player n'est stockée dans le ThreadLocal.

## API V2

`KcraftAPI.getAPIVersion()` retourne maintenant `2.0.0`.

Les lectures utilisent le `RecipeCatalog` immutable.

Les mutations API :

```text
registerCraft
unregisterCraft
```

reconstruisent immédiatement :

```text
RecipeCatalog
CompiledRecipeCatalog
RecipeIndex
```

Une recette dynamique ne tombe donc plus dans le matcher legacy.

`forceCraft` est aussi null-safe pour `consume-result:false` et est tagué
`API_FORCE`.
